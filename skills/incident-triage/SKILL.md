# 故障排查方法（先定位，后改动）

## 一、先定三件事，再碰任何配置
1. **发病时间**：去找单调计数器（日志行数、监控曲线、`uptime`、文件 mtime、账本 seq），把"从什么时候开始"钉到小时级。
2. **范围**：用户报一个对象，先数总体——同类的都病了还是只这一个？（一拉发现全类都病，是系统性原因；只这一个，才是它自己的事。）
3. **变更**：发病时间附近谁动过什么（发布、配置、证书、磁盘、上游）。

## 二、对照，别只盯着病人
- **换第二个靶子**：同样的操作打另一台/另一个对象，一次就能推翻"单机配置问题"。
- **进程在 ≠ 服务活**：状态写 RUNNING 也不算数，用真实调用验证（curl / 一条查询 / 一次真实任务）。
- **报错文本的变化**比成败更灵敏：同一个操作报错换了措辞，说明你动的东西生效了（或没生效）。
- **对方会缓存**：连通性测试可能被缓存，换端口/参数再试。
- **用户转述的归因要独立验证**：事件收下、结论别照单全收。

## 三、动手规则
- 先只读后写；每一步说清影响面；不可逆的先备份、先问；绝不批量。
- 一次只改一个变量，改完立刻用同一条验证命令复测。
- 修好后写清：根因 / 证据 / 改了什么 / 怎么验证的 / 还剩什么风险。**判据不能取自被测对象**（"它自己说好了"不算）。
